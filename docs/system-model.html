The parties, what each one holds, what each one can do, and the accounts on chain.

System model

Parties#

Holder. Has a Solana wallet and wants a certificate for a subject. Holds the wallet key, the vault ring keys derived from one wallet signature, and the revoke kits.

Subject. What the certificate is about: a wallet (kind 0), an X handle (kind 1) or a badge key made for this certificate (kind 2). On chain the subject is a 32-byte hash (CONTRACT §1).

Controller. The key that may revoke the certificate and join Rooms with it. For a wallet or a badge it is the subject key itself; for an X handle it is a key the client derives for that handle from the vault seed, so it can be rebuilt on any device by signing the same vault message again.

Browser client (client/pof-client.js). Runs the Rings SDK and its Poseidon WASM in the page. It derives the vault, registers it in the User Registry, shields SOL or USDC into it, syncs and decrypts its notes, picks the fewest notes that reach a tier, signs the subject statement, builds the disclosure package and keeps the revoke kits (exportable as a file). Nothing secret leaves the page except the package sent to the Verifier.

Vault ring. A Privacy Ring whose Ed25519 owner key is sha256("pof/vault/v2" ‖ signature) over a fixed plain-text message the wallet signs (or a random key with a passphrase backup, for wallets that do not sign deterministically). It is separate from the wallet's own ring, so the nullifier key the Verifier sees is never the main ring's. The vault key signs the disclosure message in the page and pays the relayer by withdrawal.

Verifier (verifier/). Checks a disclosure package against chain state and signs the 240-byte attestation, or refuses with a specific error code. Appends each signed attestation to the transparency log. Holds the ed25519 signing key. Keeps no amount, no opening and no nullifier key.

Transparency log. An append-only Merkle log (RFC 9162 hashing) of every attestation the Verifier signs. Its signed tree head is anchored on chain with anchor_log. Holds no amounts, openings, nullifiers or salts.

Relayer. A funded key that submits certify for X-handle and badge subjects, so the holder's wallet never signs a public transaction that names the certificate. The holder pays it the fee, the rent and the network fee in one transfer, from any wallet or as a Ring withdrawal. It refuses wallet subjects (a wallet certificate is submitted by the wallet). It caps its own spend over a rolling 24-hour window and keeps a balance floor.

Keeper. Holds each certificate's revocation pairs (salt, nullifier), sealed with AES-256-GCM, watches whether any disclosed nullifier is spent and calls revoke_spent when one is. Also anchors the log head on chain. Off before launch.

X linker. Issues a one-time code and a secret for a handle, reads the post that carries the code through fxtwitter, and for the holder of the secret issues a link id: the Verifier's own signature over the handle, the controller key and an expiry. Keeps only hashes, for at most 30 minutes.

pof program (pofP4QRRDXnmDN9CNYiAGHfwMEgM7sLWhVcUMpsbynT). Rebuilds and checks attestations, keeps the certificates, the Config (keys, fee, tier tables) and the Treasury (fees and public counters), verifies spends against the Rings accounts, and offers the CPI gate require_certificate.

pof_gate program (gatSToJMD8ZPLa85fKj6seYHUtYx4ah3ptZvLkisLPU). Rooms with an asset and a minimum tier. A controller joins with a live certificate; anyone evicts a member whose certificate is no longer good enough. No fees, no admin. The bots read it.

Witnesses. Anyone running witness/: checks each signed log head against the chain and the heads before it, cosigns it or records an alarm (CONTRACT §8).

Readers. Anyone: the /v1 API, @pof/sdk, the MCP server, the Telegram and Discord bots, other programs by CPI.

Network assumptions#

  • Slots are the only clock. Every window in the protocol is a count of slots read from the chain.
  • The Solana RPC answers honestly about account state at confirmed commitment. A lying RPC can make the Verifier refuse or, together with a lying indexer, sign over a root that is not real; the program then rejects the attestation only if it fails its own checks (the root itself is bound by the Verifier's signature, not re-read on chain).
  • Rings tree 0 (777pvSGe…) is the only tree; all notes of one attestation must be in it.
