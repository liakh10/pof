Test report: phase 2, the zero-knowledge proof of funds (zk/)

Development setup only. Every proof and every number below comes from a trusted setup made on one machine (zk/setup/TRANSCRIPT.md). Whoever ran it could forge proofs for that key. It is fit for local tests and devnet, and never for mainnet certificates. The public ceremony that replaces it is described in docs-src/zk.md ("The public ceremony"). certify_zk is not deployed anywhere, and stays off (ZkConfig.enabled = false) until that ceremony has run.

Scope:

  • zk/circuits/pof.circom: the circuit.
  • zk/js/zk.js: the circuit inputs, the context hash, the escrow, the proof encoding and the prover call. The rings client imports it.
  • zk/scripts/: build, ceremony, transcript, and the verifying key turned into Rust.
  • zk/bench/: proving in the browser.
  • zk/onchain/: the Groth16 verifier over the alt_bn128 syscalls, and the certify_zk patch for pof. apply.py applies it to a copy of program/; patch/pof-program.diff is the same change as a reviewable diff.

Toolchain: Node 20, circom 2.2.2, snarkjs 0.7.5, circomlib 2.0.5, solana-cli 4.1.2 (Agave), Anchor 1.2.0, solana-bn254 3.2.1, Chrome 158 headless.

No mainnet transaction was sent. Mainnet was read for one finalized blockhash per ceremony phase (the beacons). The client's test vectors were read earlier.

The statement, the public inputs and who sets each one are in docs-src/zk.md.

Proven against Rings (test/parity.test.mjs):

  • circomlib Poseidon equals the Helius SDK hasher for 1, 2, 3, 4 and 7 inputs;
  • hashBytes, the owner identity and the asset hash equal the SDK;
  • the circuit's commitment formula, fed with four real mainnet deposits' public data, gives exactly their leaf hashes.

The circuit tests (test/circuit.test.mjs). Each "no witness" case means the witness generator hits a failing constraint, so no proof can exist for it:

  • Valid: one note above the tier, and four notes summing exactly to the minimum (tags come out ascending). Both prove and verify, and the public signals come out in the documented order.
  • Amount below the tier: no witness.
  • Wrong root: a state root the notes are not under gives no witness. A valid proof does not verify under another state root or another nullifier root.
  • Wrong nk, wrong owner: no witness.
  • A spent note (its nullifier in the nullifier tree): no witness.
  • Replay: a proof does not verify with the context of another subject, payer, tier, asset, controller or nonce, nor with a higher minimum.

  • Malformed: no witness for any of these:

    • a non-bit enabled, the first slot unused, or a gap among the used slots;
    • a tag on an unused slot, a wrong tag, or a wrong ciphertext;
    • an ephemeral point that is not r·B8;
    • a minimum over u64, a leaf index over 32 bits, or an amount of 2^64;
    • a broken state path or nullifier path;
    • a missing signal. The same note twice is refused before proving.
  • Spend authority (ZK-04): nk and the openings without the owner's registered secret give no witness. Neither does another registry root, nor another owner's registry entry.
  • The end of the nullifier list (ZK-10): a nullifier above the last element (next = 0) proves absent. That element itself is refused.
  • A changed proof does not verify.
  • The escrow: the revocation key opens every nullifier from R and ct and checks it against the tag. Another key is refused.

The 4x throttle slows the main thread; snarkjs proves in Web Workers, which DevTools throttles less. So a real mid-range phone will be slower than the second row. A phone measurement is still to do.

The module the rings client calls is zk/js/zk.js, ESM with no dependencies:

  • buildInputs(P, { ring, notes, pub, r, registry }) takes P = fromBytesPoseidon(core.poseidon) (the SDK hasher the client already loads), the note openings and paths, the on-chain roots, and context(...).
  • prove(snarkjs, { input, wasm, zkey, onStage }) returns the proof, the public signals, the timings, and args: the certify_zk arguments as bytes.
  • Also ownerSecretFrom(seed), ownerCommitment (for register_zk_owner), escrowKeypair and openEscrow (the keeper).

bench/index.html is the reference page with a loading state.

On chain: certify_zk#

The patch adds these to pof:

  • accounts: ZkConfig ["zk"], the owner registry ["zkreg"], and NoteLock ["znote", tag];
  • instructions: set_zk, register_zk_owner, certify_zk and release_note_lock;
  • changes to existing code:
    • revoke_spent gets a zk branch (it checks Poseidon(TAG, nf) == tag);
    • gate refuses a settling zk certificate (ZK-02);
    • renew refuses zk certificates.

The Groth16 check is zk/onchain/src/groth16.rs over solana-bn254 (alt_bn128 add, mul and pairing syscalls), with A negated client side.

The suite (12 checks, onchain/test/zk-chain.mjs):

  • set_zk:
    • an outsider is refused, and so is a key off Baby Jubjub;
    • turning it on waits the rotation delay, and a ready certify_zk is refused until then;
    • turning it off is immediate;
    • the vk hash is recorded.
  • Valid certificates:
    • one note for a wallet subject: live, the ZkConfig address as the verifier, the tag stored, and the lock holds the escrow, which the keeper opens from chain data to the right nullifier;
    • four notes at tier 2 (10 SOL exactly), a badge subject, relayed by another payer;
    • USDC tier 1, with its lock address pre-funded by a stranger (ZK-07).
  • Wrong root:
    • a state root not in the history: ZkStateRootUnknown;
    • a valid proof against an older nullifier root (ZK-01), or a made-up one: ZkNullRootNotNewest;
    • an unknown registry root: ZkRegistryRootUnknown.
  • Below tier: a proof against the tier 1 minimum submitted as tier 3 gives ZkProofInvalid.
  • Replay: a proof bound to wallet 3 submitted for wallet 4, or with another payer, or with another nonce, gives ZkProofInvalid. An X subject is refused.
  • Malformed:
    • a flipped proof byte: ZkProofInvalid;
    • the same proof with a tag + r: ZkInputNotInField;
    • reversed or duplicate tags: NullHashesUnsorted;
    • missing or misordered locks: ZkLockMissing;
    • fewer ciphertexts than tags: BadNoteCount.
  • One note, one live certificate:
    • the same note for another wallet: ZkNoteLocked;
    • releasing the lock while the first certificate is live: ZkNoteStillLive;
    • after revoke_by_holder and a release, the rent goes back to its payer and the other wallet certifies.
  • revoke_spent on a zk certificate:
    • the note's nullifier PDA exists (a queued spend, exactly the case the settle window is for);
    • the keeper opens the escrow from the lock, and a wrong nullifier is refused;
    • the real one revokes it during the settle window;
    • then the lock is released.
  • Settle window (ZK-02):
    • certify_zk + require_certificate in one transaction is refused (ZkSettling);
    • the certificate's issued slot is the certify slot + 20 (quick build; 150 in the launch build);
    • the gate passes from that slot.
  • The CPI gate reads a settled zk certificate like a signed one, and refuses a higher tier.

The ceremony#

scripts/ceremony.sh, with the transcript in setup/TRANSCRIPT.md:

  • Phase 1: powersoftau new bn128 17, two random contributions, a beacon (mainnet slot 473,512,657), prepare phase2 and verify. It took 28 minutes; the 151 MB output stays out of git, sha256 cbd476d2…ac52.
  • Phase 2: groth16 setup over the r1cs, two random contributions, a beacon (mainnet slot 473,521,279), zkey verify and the exported verifying key. It took 4 minutes.

The entropy came from /dev/urandom and was never written. Labelled a development setup everywhere it appears.

What remains#

  • The public ceremony before mainnet (docs-src/zk.md), then rebuild vk.rs, publish the build hash, and set_zk.
  • The merge into pof: the program agent reviews onchain/patch/pof-program.diff and merges it with apply.py. The zk part stays off on chain until the audit re-reviews it.
  • ZK-06: the Verifier checks the znote lock of each note it attests (it knows the nullifier, so tag = Poseidon(TAG, nf)). A CONTRACT §3 v2 would let signed certificates create the locks too.
  • The rings client: register_zk_owner (one vault-key signature) and the zk certify flow with zk.js.
  • The keeper: open the escrow from NoteLock accounts, and watch new nullifiers against live zk tags.
  • The API and SDK: show a settling zk certificate as "settling" (its issued_slot is in the future).
  • A real phone measurement.
  • A devnet run against the real tree, with a real deposit, a real non-inclusion proof from the indexer, and a real spend. The local suite uses a tree account that holds synthetic roots.
  • Not in this version: X-handle subjects (they need the linker's proof in the circuit), more than 4 notes, unlinkable (salted) tags, and the subgroup check of the escrow key on chain.
