# Program test report: pof and pof_gate

Programs: `pof` `pofP4QRRDXnmDN9CNYiAGHfwMEgM7sLWhVcUMpsbynT` and `pof_gate` `gatSToJMD8ZPLa85fKj6seYHUtYx4ah3ptZvLkisLPU` (Anchor 1.2, Rust 1.89).
Source: `program/programs/`. IDLs: `program/idl/`. Generated by `program/test/report.mjs` on 2026-11-25.

## How it was tested
- **Where:** a local `solana-test-validator` (Agave 4.1) with the Helius Privacy Rings program and its tree 0 cloned from mainnet, including
  the tree's real nullifier root history, and pump.fun cloned for the launch rehearsal. Nothing was sent to mainnet; mainnet was only read.
- **The Verifier's side:** the suite holds a local ed25519 key and signs CONTRACT §3 bytes into Ed25519 program instructions, exactly as
  the off-chain Verifier must. Wrong keys, tampered bytes and replays are signed the same way.
- **Spent nullifiers, two ways:**
  - (a) nullifier PDAs written into the local chain byte for byte as a real spend leaves them: owner the Privacy Program, 11 bytes,
    first byte 8. Two look-alikes are also written (a wrong first byte, a wrong length), and they must not count.
  - (b) a **real mainnet nullifier** with its 40-level membership path from the Helius indexer, proven against the cloned tree's on-chain
    nullifier roots. The same path is also checked in a Rust unit test with `light-poseidon`.
- **Two builds:**
  - the suite runs a build whose floors are lowered (validity at least 10 slots, rotation delay at least 5, a 40-slot starting
    rotation delay), so expiry and rotation pass in seconds;
  - the rehearsal, the own-CA test and launch day deploy the launch build: validity and rotation delay both start at 216,000 slots
    (about a day), and the admin can set them from 9,000 slots up to 1,512,000 and 1,296,000.
- **Recorded runs:** each full run is unit tests → suite → wind-down on the suite's live state.
  - 2026-11-25 02:23:35 unit=8/8 suite=35/35 closing=7/7
  - 2026-11-25 02:43:11 unit=8/8 suite=35/35 closing=7/7

## Adversarial cases covered
- **Wrong Verifier key:** a random key, and the old key after rotation. Refused.
- **Tampered bytes:** tier, nonce, notes, expiry, subject, payer, or another program id in the signed bytes. Refused.
- **Signature placement:** no Ed25519 instruction; one that is not right before `certify`; one whose offsets point at instruction data
  by index instead of inside itself. Refused.
- **Replay:** the same attestation renewed, certified again while live, or resubmitted after a revoke. Refused.
- **Bad timing:** a stale attestation, a future one, a root read too long before, an expiry past the validity, an already expired one.
  Refused.
- **Bad shape:** a bad tier, asset or kind; unsorted or repeated salted hashes; note counts of 0 and 9. Refused.
- **revoke_spent:**
  - refused: a wrong salt, a wrong index, an unspent nullifier, someone else's PDA, a tree that is not the Rings program's;
  - the look-alike PDAs do not count;
  - an absent PDA never reads as unspent;
  - for the membership path, a wrong next value, a wrong leaf index, a wrong sibling or a short path are refused;
  - a double revoke is refused;
  - the staged path: refused when another revoker writes the buffer, when a level is left out, when a level is tampered with,
    when the salt is wrong, and when a buffer staged for one certificate is used for another; the buffer closes with its rent back;
  - a nullifier PDA passed as the tree is refused: only Rings tree 0 counts.
- **Gates and Rooms:**
  - `require_certificate` refuses a forged account, a wrong subject, a revoked or expired certificate, and a low tier;
  - Rooms refuse a join by a non-controller, a lower tier, another asset, or a shut room;
  - `evict` is refused while the certificate is still good, and refused with a forged certificate account or another payer;
  - `evict` works after a revoke, an expire-and-close, or a raised room tier.
- **Money:**
  - fees go only to the treasury and from there only to the dev, never into the treasury's rent;
  - rents go back exactly to whoever paid them (certificates, members, rooms);
  - a remade certificate pays its old payer exactly the rent;
  - lamports donated into a certificate go to the treasury, not to the old payer (audit POF-07);
  - a lowered rotation delay does not shorten the next rotation (audit POF-17);
  - `renew` refuses an expired certificate (audit POF-22).
- **Verifier keys (fuzz):** a revoked key signs nothing more. Its certificates then fail `require_certificate` and Rooms, their
  members can be evicted, and anyone can void them. A certificate signed by the current key stays live.
- **Admin inputs (fuzz):**
  - `anchor_log` refuses a size of 2^64 − 1, and any step over 10,000,000 entries;
  - `set_roles` refuses a token account given as the mint.

## Phase 2 (certify_zk)
- Merged from `pof/zk`, but behind the cargo feature `zk`, so the launch binary has none of it: no `certify_zk`, no `set_zk`,
  no zk accounts. It ships as a program upgrade after the public ceremony.
- The suite checks the launch build itself: no zk instruction in its IDL, no ZkConfig on chain, and an instruction carrying
  `set_zk`'s discriminator is refused.
- `zsh test/zk.sh` runs zk's own on-chain suite against this program built with the feature (IDL `idl/pof-zk.json`).
  - `certify_zk` takes about 241,000 CU for one note and about 298,000 for four.
  - The audit fixes are tested in that suite:
    - **FZ-18:** a zk certificate revoked as spent cannot be remade with the same proof (the nonce is refused). A fresh proof of
      the spent note is refused too, because its note lock is marked spent and never released.
    - **ZK-11:** owner registration is one paid record per owner (rent plus the certify fee). A second registration of the same
      owner is refused. The registry keeps 20 roots.
  - **The 4-note transaction is 1,230 bytes**, 2 bytes under the 1,232-byte limit. The plan: at most 3 notes per proof in the client,
    or 4 only through a lookup table, which removes about 400 bytes of account keys.

## What these tests do not cover
- **No real spend on the clone.** A spend needs a Groth16 proof from the Helius prover, which cannot serve a local validator.
  - The spent state is written as the bytes a spend leaves, path (a).
  - It is also proven from a real mainnet spend, path (b).
- **The one-transaction membership proof with a full 40-level path is not run here.** That path is 1,280 bytes. It needs a v1
  transaction, which mainnet accepts (Rings deposits already use it) but the local Agave 4.1 validator does not run.
  - The one-transaction proof is tested with up to 20 levels. While the nullifier tree holds under 65,536 entries, 16 are enough.
  - Past that size, which mainnet will reach soon, the **staged proof** carries all 40 levels in ordinary transactions:
    `open_path` with 20 levels, `stage_path` with 20 more, then `revoke_spent_staged`.
  - The staged proof is tested here at full depth with the real mainnet path.
- **The Verifier's own checks are not tested here.** That means commitments, tree inclusion, unspent nullifiers and note age. They are
  tested in `verifier/test`. On chain, the program trusts the Verifier's signature for them. This is the first trust point in /docs.
