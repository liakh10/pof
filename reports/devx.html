Test report: developer surfaces (API, SDK, MCP, bots)

Scope: sdk/ (@pof/sdk 0.1.0), api/v1/ and api/openapi.json, mcp/ and api/mcp.js, bots/ and api/bots.js. Every suite below runs from a clean checkout with the commands shown. Node 20, solana-cli 4.1.2 (Agave), Anchor 1.2.0 programs built from program/ at the time of the run.

SDK unit (16)#

  • Base58 and PDAs against @solana/web3.js (an independent implementation): 200 random keys round-trip and encode identically; 40 random ["cert", hash, [asset]] PDAs give the same address and bump as findProgramAddressSync; every generated keypair is on the curve and every PDA is off it.
  • Subject hashes (CONTRACT §1) against node:crypto SHA-256: wallet, badge, X handle (case and @ folded); a web3.js PublicKey is accepted; handles longer than 15 characters or with other symbols are refused.
  • Subject parsing: @h, x:h, wallet:, badge:, a bare key (tried as wallet and as badge), a 64-hex hash; empty and garbage input refused.
  • Tiers (CONTRACT §2): labels, asset parsing, unknown tiers refused. On the local validator the SDK's tier table is compared with the program's Config for all 10 asset-tier pairs (base units).
  • Account layouts from the program's IDL: Certificate encode then decode, memcmp offsets of asset and tier, a wrong discriminator and a short buffer refused, liveness at the expiry slot exactly as the program's Certificate::is_live (live at expiry_slot, expired at expiry_slot + 1).
  • Attestation bytes (CONTRACT §3, 240 bytes): built and parsed back field for field, offsets of tier, root_slot, expiry_slot, controller and nonce checked against the table.
  • Transparency log (CONTRACT §7), against a reference RFC 9162 implementation written separately in the test: roots of every tree size 1 to 33 match; inclusion proofs for every index of every size 1 to 33 verify, and fail with a wrong leaf, a tampered path node or a shortened path; consistency proofs for every pair of sizes up to 20 verify and fail with a wrong old root. Signed tree heads (80 bytes) verify with a real Ed25519 key and fail with a changed size; a 377-byte leaf parses; verifyLogEntry passes end to end and fails with the wrong index, a forged attestation byte, or a head key outside the trusted set.
  • Client on an in-memory chain: lookups by wallet, handle, badge, bare key and hash; every checkProofOfFunds reason (ok, below_tier, expired, revoked_spent, no_certificate); list filters by asset, tier, minimum tier, status and kind; stats; an account owned by another program at a certificate address is ignored; rooms with members and their live status; Config (verifier rotation applies at its slot) and Treasury counters.
  • CPI accounts: require_certificate accounts and data, out-of-range tier refused; pof_gate.join member PDA checked against web3.js; conversion to a web3.js TransactionInstruction.

SDK on a local validator (7)#

A fresh solana-test-validator with pof.so and pof_gate.so loaded as upgradeable programs (a throwaway upgrade authority), devx's own ports, 16 ticks per slot. init_config and certify are sent with the program's own IDL builder; everything a developer touches goes through the SDK and devx code. The validator is stopped and its ledger deleted after the run.

  1. Program ids, Config and Treasury PDAs, active verifier, relayer, fee and all tier minimums read correctly.
  2. Three real certify transactions (an Ed25519-signed 240-byte attestation each: a wallet subject paid by its holder, an X-handle subject paid by the relayer, a tier 1 wallet) read back through lookup, checkProofOfFunds, listCertificates (asset, tier and kind filters on a real getProgramAccounts) and stats (the Treasury's live count and live tier-minimum sum).
  3. require_certificate with the SDK's accounts and data: accepted at the certificate's tier, with the CertView return data decoded (kind, tier, controller); refused with TierTooLow one tier above.
  4. pof_gate: a room created; the wallet holder and the X-handle certificate's controller join with joinRoomInstruction; the tier 1 holder is refused with TierTooLow; the room reads back with its name, tier and two live members.
  5. revoke_by_holder: the SDK reads revoked_by_holder with the revoke slot; checkProofOfFunds gives that reason; the room shows the member as not live; a third party evicts it; the Treasury counts the revocation.
  6. anchor_log: the head computed by the SDK over the three log leaves is signed by the Verifier key and anchored; the Treasury holds the same size and root; every leaf's inclusion proof verifies against it.
  7. The /v1 router, the MCP check_proof_of_funds tool and the bots' gate decision all read the same chain and agree (@localwhale passes tier 5; the revoked wallet reads revoked_by_holder; stats and config match).

Not covered here: revoke_spent (it needs the cloned Privacy Rings program and a real nullifier PDA; the program and verifier suites cover it) and renew/expire.

HTTP API (12)#

Router tests and the real Vercel entry behind a Node HTTP server, with the chain served by a JSON-RPC mock built from the in-memory accounts and the log served in the Verifier's exact shape:

  • every endpoint answers with the documented shape; CORS * and preflight 204; 405 for writes; cache headers per endpoint (s-maxage 5 to 300, no-store on upstream errors);
  • the gate check for each reason; an unknown subject is 200 with an empty list;
  • a clear 400 for a bad subject, an unknown asset, minTier without asset, a tier out of range, an unknown status or kind, a room that is not an address; 404 for unknown routes, rooms and log entries; 503 without an RPC; 502 when the RPC fails;
  • paging (limit, cursor, nextCursor);
  • /v1/log/proof/{id} verifies all entries, and a tampered proof from the log is reported as verified: false with checks.included: false, never passed through;
  • the OpenAPI file is served and lists every route.

MCP (3)#

The official client (@modelcontextprotocol/sdk 1.32.2) connects over stdio (spawning node mcp/stdio.js against the JSON-RPC mock) and over Streamable HTTP (the hosted handler behind a Node server). On both: initialize, server info and instructions, tools/list (8 tools, read-only annotations), calls of every tool with yes and no answers (including min_amount mapped to a tier and the "funds moved" reason), tool errors returned as isError results, an unknown tool rejected, ping. Over raw HTTP: GET is 405, notifications are 202, CORS preflight, protocol version negotiation (2024-11-05 echoed, unknown versions answered with 2025-11-25), batches, a parse error is 400.

Bots against mocks (9)#

Recorded Telegram Bot API and Discord REST calls, Discord interactions signed with a real Ed25519 key, wallet link signatures from real Ed25519 keys, the in-memory chain.

  • Link tokens: expiry, platform and user binding, tampering refused; a short secret refused.
  • Telegram: the webhook secret is enforced; only admins bind a group; an unlinked requester is held and sent a personal link, then approved in the same call that completes the link; a linked small holder is declined with the reason; a linked whale is approved at once; unbound groups are left alone; /start, /status, /unlink.
  • Linking: a signature by another key, an unreadable signature, and a signature made for another user are refused; a subject linked from a second account moves; X handles through the Verifier's link id (good, unknown, wrong handle).
  • Discord: bad signatures are 401; PING answers PONG; setup needs Manage Roles and a real Room; /pof-verify offers a personal link, the link grants the role; after a revocation the sweep removes the role, and a second sweep does nothing; /pof-verify then says the funds moved; /pof-unlink.
  • Telegram sweep removes a revoked member (ban then unban, so they can ask again) only where /pof_evict on is set.
  • Paused sweep and unconfigured bots answer clearly.

Not covered: the live Telegram and Discord platforms (their tokens are the owner's to create; the setup scripts print each step's result) and Vercel Blob itself (the bots use the same private-store calls as the Verifier).
