Program test report: pof and pof_gate

Programs: pof pofP4QRRDXnmDN9CNYiAGHfwMEgM7sLWhVcUMpsbynT and pof_gate gatSToJMD8ZPLa85fKj6seYHUtYx4ah3ptZvLkisLPU (Anchor 1.2, Rust 1.89). Source: program/programs/. IDLs: program/idl/. Generated by program/test/report.mjs on 2026-11-25.

How it was tested#

  • Where: a local solana-test-validator (Agave 4.1) with the Helius Privacy Rings program and its tree 0 cloned from mainnet, including the tree's real nullifier root history, and pump.fun cloned for the launch rehearsal. Nothing was sent to mainnet; mainnet was only read.
  • The Verifier's side: the suite holds a local ed25519 key and signs CONTRACT §3 bytes into Ed25519 program instructions, exactly as the off-chain Verifier must. Wrong keys, tampered bytes and replays are signed the same way.
  • Spent nullifiers, two ways:
    • (a) nullifier PDAs written into the local chain byte for byte as a real spend leaves them: owner the Privacy Program, 11 bytes, first byte 8. Two look-alikes are also written (a wrong first byte, a wrong length), and they must not count.
    • (b) a real mainnet nullifier with its 40-level membership path from the Helius indexer, proven against the cloned tree's on-chain nullifier roots. The same path is also checked in a Rust unit test with light-poseidon.
  • Two builds:
    • the suite runs a build whose floors are lowered (validity at least 10 slots, rotation delay at least 5, a 40-slot starting rotation delay), so expiry and rotation pass in seconds;
    • the rehearsal, the own-CA test and launch day deploy the launch build: validity and rotation delay both start at 216,000 slots (about a day), and the admin can set them from 9,000 slots up to 1,512,000 and 1,296,000.
  • Recorded runs: each full run is unit tests → suite → wind-down on the suite's live state.
    • 2026-11-25 01:13:25 unit=7/7 suite=32/32 closing=7/7
    • 2026-11-25 01:19:42 unit=7/7 suite=32/32 closing=7/7

The suite, check by check#

  • ✓ init_config: only the program's upgrade authority (an outsider refused); launch settings, SOL and USDC tiers
  • ✓ set_params: admin only, bounds held (fee above the 0.25 SOL cap, validity under the floor, zero lag refused)
  • ✓ set_fee: capped at 0.25 SOL, admin only
  • ✓ set_asset: a new table in a free slot (ascending, no gaps); a set table only toggles enabled
  • ✓ certify a wallet subject: the signed 240 bytes match, the fee goes to the treasury, every field stored
  • ✓ certify refuses: a wrong Verifier key, tampered bytes (tier, subject, notes, nonce), another program id, another payer
  • ✓ certify refuses: no Ed25519 instruction, one not right before, one whose offsets point at another instruction
  • ✓ certify refuses: stale, from the future, root too old, expiry past the validity or already passed, bad tier, asset, kind, notes
  • ✓ certify refuses a second live certificate for the same subject and asset (renew instead); USDC is a separate one
  • ✓ an X-handle subject through the relayer: no on-chain fee (paid privately), the controller is a separate key, counted as relayed
  • ✓ a badge subject: the badge key is the controller; its hash is checked on chain
  • ✓ renew: same notes, subject, asset and controller with a newer attestation; tier, root and expiry move; fee charged
  • ✓ revoke_spent (a): the nullifier PDA a real spend leaves; wrong salt, an unspent nullifier, a forged PDA and look-alikes refused
  • ✓ revoke_spent (b): a real mainnet nullifier, its PDA absent here, proven spent by its path in the cloned nullifier tree
  • ✓ revoke_by_holder: only the controller (the X-handle key, not the relayer that paid); then a replay of the old attestation is refused
  • ✓ revoke_signed: the controller signs the 156 POF-REVOKE1 bytes, the relayer submits and pays, no wallet signs; a wrong key, tampered bytes, another certificate, a replay, a lapsed valid_until and a signature from before a remake refused
  • ✓ certify over a revoked certificate: a newer attestation remakes it; its old payer gets the rent back (and must be passed)
  • ✓ audit POF-07: lamports donated into a revoked certificate never reach the prior payer; the remake costs the rent alone, the surplus goes to the treasury
  • ✓ expire: refused before the expiry slot; after it anyone closes the account, the rent goes back to the payer exactly
  • ✓ an expired-but-unclosed certificate is not live for gates, and certify may remake it in place
  • ✓ set_roles: the root mint once; a payer holding 1,000,000 $ROOT pays no fee, 999,999 pays, a wrong holder account is refused
  • ✓ Verifier rotation: proposed by the admin only; the old key signs until the delay passes, then only the new one; apply_verifier records it
  • ✓ set_paused: certify and renew stop at once, revocations and expiry do not; admin only
  • ✓ anchor_log: the §7 signed tree head by the active Verifier key; it only grows; another key or another program id refused
  • ✓ withdraw_fees: admin only, to the dev wallet only, never into the treasury's rent
  • ✓ require_certificate (CPI helper, called directly): live and tier, asset, tier floor, a forged account and a wrong subject refused
  • ✓ pof_gate create_room / set_room: tiers checked against POF's table; creator only
  • ✓ join: through the require_certificate CPI; a lower tier, another asset, a non-controller, a revoked one and a shut room refused
  • ✓ evict: refused while the certificate is good; after a revoke anyone evicts, the rent back to the member's payer; a forged certificate account refused
  • ✓ evict: a member whose certificate expired and closed, and a member below a raised room tier
  • ✓ leave: only the member's controller; close_room refused while members remain, then the creator closes it
  • ✓ the treasury counters agree with the certificate accounts on chain

Adversarial cases covered#

  • Wrong Verifier key: a random key, and the old key after rotation. Refused.
  • Tampered bytes: tier, nonce, notes, expiry, subject, payer, or another program id in the signed bytes. Refused.
  • Signature placement: no Ed25519 instruction; one that is not right before certify; one whose offsets point at instruction data by index instead of inside itself. Refused.
  • Replay: the same attestation renewed, certified again while live, or resubmitted after a revoke. Refused.
  • Bad timing: a stale attestation, a future one, a root read too long before, an expiry past the validity, an already expired one. Refused.
  • Bad shape: a bad tier, asset or kind; unsorted or repeated salted hashes; note counts of 0 and 9. Refused.
  • revoke_spent:
    • refused: a wrong salt, a wrong index, an unspent nullifier, someone else's PDA, a tree that is not the Rings program's;
    • the look-alike PDAs do not count;
    • an absent PDA never reads as unspent;
    • for the membership path, a wrong next value, a wrong leaf index, a wrong sibling or a short path are refused;
    • a double revoke is refused.
  • Gates and Rooms:
    • require_certificate refuses a forged account, a wrong subject, a revoked or expired certificate, and a low tier;
    • Rooms refuse a join by a non-controller, a lower tier, another asset, or a shut room;
    • evict is refused while the certificate is still good, and refused with a forged certificate account or another payer;
    • evict works after a revoke, an expire-and-close, or a raised room tier.
  • Money:
    • fees go only to the treasury and from there only to the dev, never into the treasury's rent;
    • rents go back exactly to whoever paid them (certificates, members, rooms);
    • a remade certificate pays its old payer exactly the rent;
    • lamports donated into a certificate go to the treasury, not to the old payer (audit POF-07);
    • a lowered rotation delay does not shorten the next rotation (audit POF-17);
    • renew refuses an expired certificate (audit POF-22).

What these tests do not cover#

  • No real spend on the clone. A spend needs a Groth16 proof from the Helius prover, which cannot serve a local validator.
    • The spent state is written as the bytes a spend leaves, path (a).
    • It is also proven from a real mainnet spend, path (b).
  • 40-level membership paths need a v1 transaction. A full path is 1,280 bytes and does not fit a legacy or v0 transaction.
    • Paths of up to about 20 given levels fit a v0 transaction. While the nullifier tree holds under 65,536 entries, 16 levels are enough.
    • Unit tests check the full 40 levels.
  • The Verifier's own checks are not tested here. That means commitments, tree inclusion, unspent nullifiers and note age. They are tested in verifier/test. On chain, the program trusts the Verifier's signature for them. This is the first trust point in /docs.
